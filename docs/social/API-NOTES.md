# Klippy Social: platform API notes

Researched from the official Meta and LinkedIn developer documentation on 2026-09-07, with every claim independently re-checked against the cited page by a second pass. This file is the source of truth for the adapters in `api/src/lib/social/adapters/`. Platform APIs change; when a page cited here moves or a limit changes, fix the row here first, then the adapter.

## How to read this

Every fact has a row id such as `M-AUTH-07`, `IG-PUB-12`, `LI-UP-03` or `X-ERR-04`. Adapter code cites the id of the row it implements in a comment beside the call, so a change in the docs can be traced to the code it affects. Rows in the main tables were verified against the cited page. Anything the second pass could not confirm is listed under "Unverified, do not build on" and is not in a table. Where a network cannot do something the brief wanted, it is listed under "Not possible on this network" and the UI must not offer it. "Source" is the documentation page the row came from.

Gotchas. The whole Meta side is gated by three separate approvals that must all be complete before a client Page admin without an app role can connect: per-permission Advanced Access via App Review (M-AUTH-39, M-AUTH-43), Business Verification (M-AUTH-35) and Tech Provider access verification (M-AUTH-36), and FLB grants are all-or-nothing (M-AUTH-05), so do not build any UI for partial grants, for connecting a Page from a non-role user before those approvals, or for publicly visible posts while only Standard Access is held (posts made then are visible to role users only per M-AUTH-38). Do not build a server-side refresh for the Facebook long-lived user token: none is documented (only Instagram-Login tokens have /refresh_access_token, M-AUTH-10), so rely on non-expiring Page tokens (M-AUTH-21) and re-run login when the user token lapses; likewise instagram_basic, instagram_content_publish and instagram_manage_insights are absent from the non-expiring list (M-AUTH-19), so IG access dies after 90 days of user inactivity and the connection screen must watch data_access_expires_at from debug_token (M-AUTH-25). Business Login for Instagram (M-AUTH-09, M-AUTH-10) cannot reach a Facebook Page, has no hashtag search, product tagging or ads, and is a fallback only; going live as an FLB app without Advanced Access to public_profile is also not possible (M-AUTH-43). Page Insights is unavailable for Pages under 100 likes and a batch of Page Insights metrics is deprecated by June 15, 2026 (M-AUTH-16), so metric choice must be checked against the referenced blog post before the analytics adapter is written. Rows M-AUTH-51 to M-AUTH-67 come from the verifier's missed list; several are publishing or insights facts recorded here so they are not lost, and where the verifier named a doc page rather than a URL the Source is the canonical path for that reference and should be click-checked before an adapter cites it. LinkedIn has one token type: a 60-day member access token, and nothing in the docs gives Klippy a Page-level or non-expiring token. Unless LinkedIn has enabled programmatic refresh on the app (detect it by the presence of refresh_token in the token response), the only renewal path is the agency user going back through the browser flow before day 60, so the connection record needs an expires_at and a reminder, not a cron refresh. Request the Community Management API on a brand new app with no other products; the request option is grayed out otherwise, and a rejection burns the app. Before that approval the only thing that works is personal-profile posting through the self-serve products. Every /rest call needs both Linkedin-Version: 202608 and X-Restli-Protocol-Version: 2.0.0, and the Dev tier caps (500 per app, 100 per member, per UTC day, no BATCH_GET) apply until Standard tier, which must be applied for within twelve months. The docs do not offer a way to grant Page roles via the API, and there are no items the UI can offer for that: the client adds the agency member as ADMINISTRATOR on LinkedIn itself.

LinkedIn never fetches media from a URL, so the public tokenised media URL approach built for Meta does not apply and no UI should promise it: the cron streams the bytes from Klippy storage to LinkedIn's upload URLs itself, within its time budget. Images are one PUT with a Bearer header; videos are 4,194,304-byte parts with no Authorization header, ETags kept in order, then a mandatory finalizeUpload. Both media types must reach status AVAILABLE before the post is created or the post will be invisible, and there is no synchronous upload mode, so the adapter needs an upload job that polls across ticks. A w_member_social-only token cannot GET /rest/images to poll status on the versioned gateway, which matters for personal-profile posting. Image byte limits are unpublished (pixel count and format only), so surface 413 and 415 as user-facing errors.

### LinkedIn

- Media ingestion from a URL: LinkedIn never downloads media from a public URL; both /rest/images and /rest/videos hand back LinkedIn upload URLs and Klippy must PUT the bytes itself (single PUT with Bearer header for images; 4,194,304-byte parts with no auth header then finalizeUpload for video).
- Any organisation action before Community Management API approval: posting as a Page, organizationAcls, share, follower and page statistics and organisation comments all need scopes granted only on approval. Before approval only personal-profile posting via Share on LinkedIn plus Sign In with LinkedIn using OpenID Connect is possible.
- Requesting the Community Management API on an app that already has other products: the option is greyed out unless the app is new with no other API products; Dev tier also requires a registered legal organisation, verified business email and a Page super admin verifying the app.
- Automatic refresh of expiring tokens for every app: programmatic refresh tokens are issued only to apps LinkedIn has enabled. Without refresh_token in the token response the only refresh path is the agency user re-authorizing in a browser before day 60; the cron cannot do it.
- Granting or changing Page admin roles through the API: access to a Company Page cannot be granted or updated through the API; the client must add the agency member as ADMINISTRATOR in the LinkedIn UI.
- Native scheduling or drafts: lifecycleState PUBLISHED is the only value accepted on create; DRAFT cannot be created through the API and there is no scheduled-publish field. Scheduling stays a Klippy cron concern.
- Editing media, article content, visibility or author of a published post: PARTIAL_UPDATE only accepts commentary, contentCallToActionLabel, contentLandingPage, lifecycleState and adContext. Changing an image means delete and re-create.
- Batch operations at Development tier: BATCH_GET is disabled (no batch posts, images, videos, socialMetadata or socialActions reads); batch delete of posts is never supported; the app is capped at 500 calls per day and 100 per member per day until Standard tier.
- Automatic link previews: the Posts API does not support URL scraping for article post creation; Klippy must supply title (required, under 400 chars), description and an Images-API-uploaded thumbnail itself.
- Time-bound (daily) statistics for a specific post: per-share and per-ugcPost queries on organizationalEntityShareStatistics are lifetime only, cover only a rolling 12-month window, return organic data only, and omit posts with zero activity.
- Listing or measuring a member's personal posts through the Posts API: retrieving posts authored by a person needs r_member_social, which is closed to new requests. Personal post analytics exist only via r_member_postAnalytics (202506+) on memberCreatorPostAnalytics, not organizationalEntityShareStatistics.
- Organic carousel posts: carousel is sponsored only; multi-image (2 to 20 images) is the organic alternative.
- Displaying a LinkedIn Page feed off-platform: not an approved use case per the Marketing FAQ; data storage rules cap stored member content at 48 hours and org social activity at six weeks or six months, so a full historical post archive inside Klippy is not permitted.
- Using deprecated API versions: 202508 and earlier are already sunset (202508 on 2026-08-17); a deprecated or missing Linkedin-Version header returns an error; 202509 sunsets 2026-09-15.

## Conflicts with the build brief

The brief made assumptions before the docs were read. Each is confirmed, corrected or left unverified below. The three KLIPPY entries come from the Klippy codebase itself, not from vendor docs, and are the ones that change the Phase 2 design.

### From the Klippy codebase

- KLIPPY-ROBOTS-01: web/public/robots.txt serves "User-agent: *" with "Disallow: /api/". The brief's public media route is GET /api/v1/m/:publicToken. Per the verified Meta rules on media fetching (host must not block the crawler in robots.txt), Instagram and Facebook would refuse to fetch every image as designed. Must be resolved in Phase 2 (explicit Allow for /api/v1/m/ plus a facebookexternalhit block, or serve media off a non-/api path). No .htaccess exists in web/ that would interfere.
